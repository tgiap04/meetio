## A. Mobile library — `@react-native-google-signin/google-signin`

### 1. Version compatible with Expo SDK 57 / RN 0.86.3
**Fact:** Latest published version is `16.1.5`. Its `peerDependencies` are `{ expo: '>=52.0.40', react: '*', 'react-native': '*' }`, and the official install docs additionally state minimum supported RN is `0.76.0`, Expo `52.0.40`, `compileSdkVersion >= 35`, `kotlinVersion >= 2.0.21`. Our stack (Expo ~57.0.23, RN 0.86.3) is above all these floors.
**Source:** `npm view @react-native-google-signin/google-signin peerDependencies` (live); https://react-native-google-signin.github.io/docs/install
**Confidence:** High (primary registry + official docs agree).

### 2. Expo config plugin — exact app.json shape
**Fact:** The plugin is registered by the package name itself: `"@react-native-google-signin/google-signin"`. Two setup paths:
- **Without Firebase:** plugin option `iosUrlScheme` (required) — the "iOS URL scheme" a.k.a. **reversed client ID**, generated by Google Cloud Console alongside the iOS OAuth Client ID when you create it.
- **With Firebase Auth:** options `googleServicesFile` for Android (`google-services.json`) and iOS (`GoogleService-Info.plist`) instead of `iosUrlScheme`.
Example (non-Firebase path):
```json
"plugins": [
  "expo-router",
  ["@react-native-google-signin/google-signin", { "iosUrlScheme": "com.googleusercontent.apps.XXXX-YYYY" }]
]
```
Requires `expo prebuild` (CNG) — the docs literally instruct running `npx expo prebuild --clean` to regenerate `ios/`/`android/`. This matches this repo's CNG setup where `android/`/`ios/` are gitignored.
**Source:** https://react-native-google-signin.github.io/docs/setting-up/expo
**Confidence:** High (official docs, directly fetched).
**Caveat (see pitfall #13):** a real, open-ish class of GitHub issues (#1313, #1280) shows the plugin-set `iosUrlScheme` sometimes does not survive `expo prebuild --clean` into `Info.plist`'s `CFBundleURLTypes`, producing `NSInvalidArgumentException: missing support for URL schemes`. Mitigation reported by users: also set `ios.infoPlist.CFBundleURLTypes` directly in `app.json` with the same reversed-client-id scheme, in addition to the plugin option. — **Confidence: Medium** (community-reported workaround, not an official doc statement).

### 3. Current API surface (this applies to v16.1.5, the "Original" module, not the newer "Universal"/One Tap module)
```ts
GoogleSignin.configure(options?: ConfigureParams): void
GoogleSignin.hasPlayServices(options?): Promise<boolean>   // always resolves true on iOS
GoogleSignin.signIn(options?): Promise<SignInResponse>      // SignInResponse = SignInSuccessResponse | CancelledResponse
```
`SignInSuccessResponse` shape:
```ts
{
  type: "success",
  data: {
    user: { id, email, name, givenName, familyName, photo },
    idToken: string | null,
    serverAuthCode: string | null,
    scopes: string[]
  }
}
```
Helpers: `isSuccessResponse(response)` (checks `response.type === "success"`), `isErrorWithCode(err)` (type guard for native error with `.code`), `isCancelledResponse`, `isNoSavedCredentialFoundResponse`. `statusCodes` includes `IN_PROGRESS`, `NULL_PRESENTER`, `PLAY_SERVICES_NOT_AVAILABLE`.

**This nested `data.*` shape (vs. flat `userInfo.*`) is the v13+ breaking change** — a WebSearch cross-check independently states "data previously accessed directly on `userInfo` will now be nested in `userInfo.data`" between the old and new major versions. Since 16.1.5 is what npm currently serves, **assume the nested shape is what you get**, and do NOT write code against the old flat `userInfo.user.email` shape found in older tutorials/blog posts (most tutorials online predate this change).
**Source:** https://react-native-google-signin.github.io/docs/api, https://react-native-google-signin.github.io/docs/original, cross-checked via WebSearch (GitHub releases/issue commentary).
**Confidence:** High for the current shape (fetched directly from the live "api" doc page); Medium for the precise version number where the breaking change landed (I could not pin the exact version, e.g. "v13.0.0" — see Unverified).

### 4. Which client IDs `configure()` needs, and why
**Fact:** `webClientId` — "client ID of type WEB for your server. Required to get the `idToken` on the user object, and for offline access." This is documented to be needed on **both** Android and iOS if you want `idToken` populated. `iosClientId` is optional/separate and used when you are not registering a webClientId path, or to override the client id used for the native iOS flow specifically (as distinct from Firebase-driven `GoogleService-Info.plist` auto-detection).
**Source:** https://react-native-google-signin.github.io/docs/original (direct quote fetched: "Required to get the idToken on the user object, and for offline access").
**Confidence:** High for the "webClientId required for idToken" fact (direct official quote). **Medium** for the precise mechanical reason "why iOS also needs webClientId to get an idToken" — the official docs state the *requirement* but do not explain the underlying OAuth mechanism in the pages fetched; I could not find an official passage spelling out that the resulting ID token's `aud` equals the webClientId. This is consistent with how Google Sign-In SDKs work generally (the web/server client ID acts as the audience for a token meant to be verified by your backend), and is corroborated indirectly by Google's own `aud` verification guidance (Q10/Q11 below) which treats the web client ID as the one your backend checks against — but I did NOT find a single source stating this explicitly for this exact library. **Flagging this as inferred, not confirmed — do not treat as settled fact.**

### 5. Expo Go
**Fact, confirmed:** "This package cannot be used in Expo Go because it uses native code." A development build (`expo prebuild` + native build, or EAS dev client) is required.
**Source:** https://react-native-google-signin.github.io/docs/setting-up/expo (direct fetch).
**Confidence:** High.

### 6. Android: Google Cloud Console registration + SHA-1
**Fact:** You must register a SHA-1 certificate fingerprint per signing configuration — debug, release, Play App Signing, and EAS Build credentials are each distinct and each needs its own registered Android OAuth Client ID (the docs note you don't need to keep/use the resulting Android client ID value anywhere in code — "the only goal here is for them to be created"). Package name must match your Android `applicationId`.
**Command to print the debug SHA-1** (the official doc references `cd android && ./gradlew signingReport`, but the classic universal `keytool` command for the default Expo/RN debug keystore is):
```
keytool -list -v -alias androiddebugkey -keystore ~/.android/debug.keystore -storepass android -keypass android
```
(Default debug keystore path/alias/passwords are Android tooling defaults, not specific to this library — standard for any RN/Expo CNG debug build.)
**Source:** https://react-native-google-signin.github.io/docs/setting-up/get-config-file (official, direct fetch, for the `gradlew signingReport` route and the "register every signing config" requirement); the `keytool` command itself is standard Android tooling knowledge, not from this doc page — **flagging this specific command as Medium confidence** since I did not find it verbatim on the library's own docs (they point at `gradlew signingReport` instead).
**Confidence:** High for "register per signing-config SHA-1, package name must match" (official, direct quote). Medium for the exact `keytool` invocation (standard Android convention, not verbatim-sourced from official google-signin docs).

### 7. Does it reliably return `idToken`, and is `serverAuthCode` needed for auth-only use case?
**Fact:** `idToken` is populated when `webClientId` is configured (see Q4) — this is the documented mechanism for getting it. `serverAuthCode` is explicitly documented as "not null only if a valid `webClientId` and `offlineAccess` was enabled in `configure()`" — i.e. it requires an **extra opt-in flag** (`offlineAccess: true`) beyond just `webClientId`. Since the task's use case is "authenticate only, do not call Google APIs on the user's behalf," you do **not** need `offlineAccess: true` and therefore do **not** need `serverAuthCode` — you only need `idToken`, which comes from `webClientId` alone.
**Source:** https://react-native-google-signin.github.io/docs/api (direct fetch, the `serverAuthCode` field description).
**Confidence:** High.

### 8. Jest mock story
**Fact:** The library ships an **official Jest mock** at `@react-native-google-signin/google-signin/jest/build/jest/setup.js`, added specifically so importing this module doesn't crash Jest (native code can't run in Node). Wire it via Jest config:
```json
{ "setupFiles": ["./node_modules/@react-native-google-signin/google-signin/jest/build/jest/setup.js"] }
```
By default the mock simulates successful calls and returns mock user data; you can override per-test with `jest.mock()`/`jest.fn()` for specific methods (`signInSilently`, `hasPlayServices`, `revokeAccess`, etc.) if you need failure-path coverage.
**This means it does NOT behave like `expo-audio`** (per your framing) — unlike libraries with no test story that crash on import, this one has a first-party, documented Jest setup file specifically to prevent that crash.
**Source:** https://react-native-google-signin.github.io/docs/testing (direct fetch); corroborated by WebSearch hit on the GitHub PR that introduced it ("feat: add jest mock (#492)").
**Confidence:** High.

## B. Server-side ID token verification (NestJS, pure ESM)

### 9. `google-auth-library` vs generic JWKS (`jose`)
**Fact:** Google's own official guidance says: **"we strongly recommend using a Google API Client Library for your platform, or a general-purpose JWT library."** Both are officially sanctioned — `google-auth-library`'s `OAuth2Client.verifyIdToken()` is the "client library" path; `jose` + Google's JWKS endpoint is the "general-purpose JWT library" path. Neither is stated as more "recommended" than the other in that phrasing — they're offered as equal alternatives.
**Versions / ESM fit:**
- `google-auth-library@11.1.0` (latest) requires **Node >=22**. `google-auth-library@10.x` requires Node >=18. Neither `google-auth-library` version declares `"type": "module"` in its own package.json (`npm view ... type` returned empty → defaults to CommonJS) — but this is a non-issue in **our** direction: pure-ESM Nest can `import` a CJS package without friction (the ERR_REQUIRE_ESM failure mode only bites the reverse direction — a CJS/legacy Nest app trying to `require()` an ESM-only package). So `google-auth-library` in this pure-ESM NestJS app works cleanly via a normal `import { OAuth2Client } from 'google-auth-library'`.
- `jose@6.2.12` (latest) is **ESM-only** (`"type": "module"`). This is also friction-free here since the whole Nest app is already ESM.
**Verdict:** Both work cleanly in this specific pure-ESM Nest 12 setup — the earlier-generation "NestJS + ESM-only package" pain (the `ERR_REQUIRE_ESM` failure mode found via WebSearch, e.g. `better-auth`+`jose` issues, langchain issues) is specifically about **CJS Nest apps** importing ESM packages. This repo's Nest app is already `"type": "module"`, so that failure mode does not apply here in either direction.
**Recommendation:** `google-auth-library`'s `verifyIdToken()` — it's a single call that already implements JWKS fetch/cache/rotation, signature check, and `iss`/`aud`/`exp` validation for you (see Q10). Rolling your own `jose` + JWKS wiring duplicates logic Google's own library already gives you correctly (this is a YAGNI call, not a compatibility one — both are technically fine here).
**Source:** https://developers.google.com/identity/gsi/web/guides/verify-google-id-token (direct fetch, the strong-recommend quote + JWKS URLs); `npm view google-auth-library engines` / `npm view google-auth-library type` / `npm view jose type` (live registry checks); WebSearch cross-check on ERR_REQUIRE_ESM failure mode direction.
**Confidence:** High on the version/engine facts (live registry). High on Google's own dual-recommendation quote (direct official fetch). Medium on the "no ESM friction here" conclusion — this is my own correct-but-inferred reasoning from the ESM/CJS interop model, not a sentence lifted from a doc that discusses this exact NestJS scenario.

### 10. Claims that MUST be validated
**Fact, per Google's official docs (two independently fetched official pages agree):**
- `iss` — must equal `"accounts.google.com"` or `"https://accounts.google.com"`
- `aud` — must match one of your app's registered client IDs
- `exp` — token must not be expired
- Signature — must validate against Google's rotating public keys
- `email_verified` — must be checked before trusting `email`; Google states it is authoritative for `@gmail.com` addresses and Workspace accounts where `email_verified` is true and `hd` is present, but NOT for external/legacy addresses without the `hd` claim — "password or other challenge methods are recommended" in that case.
- `hd` — optional, only relevant if you restrict sign-in to a specific Workspace domain (not applicable to a general consumer sign-in flow).
**JWKS endpoints** (needed if going the `jose` route): JWK format `https://www.googleapis.com/oauth2/v3/certs`, PEM format `https://www.googleapis.com/oauth2/v1/certs`. Keys rotate; respect the `Cache-Control` header for refresh timing (don't hardcode/cache forever).
**Source:** https://developers.google.com/identity/sign-in/android/backend-auth and https://developers.google.com/identity/gsi/web/guides/verify-google-id-token — both fetched directly, both official, and they agree on `iss`/`aud`/`exp`.
**Confidence:** High.

### 11. `aud` handling with multiple client IDs (mobile signs in with `webClientId`)
**Fact:** When the mobile app is configured with `webClientId` (per Q4/A above), the resulting ID token's audience should be that web client ID. `google-auth-library`'s `verifyIdToken({ idToken, audience })` accepts `audience` as **either a single string or an array of strings** — this is the documented mechanism for accepting tokens whose `aud` may legitimately vary (e.g. if you also accept tokens from a web frontend using a different client ID). Given this repo's design (mobile-only, one shared `webClientId` used by both iOS and Android configs), you likely only need to check against a single audience value — the web client ID — but the array form is there if you add a web client later.
**Source:** WebSearch synthesis of `googleapis/google-auth-library-nodejs` source/issues (`oauth2client.ts`, issue #326) plus Google's own web backend-auth guide, cross-referenced against the `verifyIdToken` signature.
**Confidence:** Medium-High — the array-audience capability is corroborated by multiple independent sources (library source code reference + issue thread + Google's official web guide pattern), but I did not independently open `oauth2client.ts` myself to quote the exact TypeScript signature; this is one level removed from a direct fetch. Treat "audience accepts string | string[]" as verified-by-strong-consensus, not verbatim-quoted.
**On "iosClientId also needs to be an accepted audience":** because `idToken` in this library is documented to be minted using `webClientId` (not `iosClientId`/`androidClientId`) on both platforms (Q4), you should **not** need to add iOS/Android client IDs to your accepted `audience` list for `idToken` verification — those platform-specific client IDs are for native OAuth handshake/account-picker purposes, not for `idToken` audience. **This inference carries the same Medium confidence caveat as Q4** — the "why" wasn't found spelled out verbatim in the docs I could fetch.

### 12. `sub` vs email as join key
**Fact:** Google's official Android backend-auth doc states plainly: "This ID is unique to each Google Account, making it suitable for use as a primary key during account lookup. Email is not a good choice because it can be changed by the user."
**Source:** https://developers.google.com/identity/sign-in/android/backend-auth (direct fetch, verbatim quote).
**Confidence:** High.

## C. Pitfalls — real-world failure modes for this exact combination

1. **iOS `iosUrlScheme` dropped by `expo prebuild --clean`.** GitHub issues #1313 and #1280 on `react-native-google-signin/google-signin`, and a related upstream Expo issue (`expo/expo#36412`, "ios.infoPlist.CFBundleURLTypes ignored by prebuild --clean; Info.plist gets exp+<slug> scheme despite config") document that CNG can regenerate `Info.plist` with the wrong URL scheme (`exp+<slug>` instead of the reversed client ID), causing `NSInvalidArgumentException: Your app is missing support for the following URL schemes`. Mitigation reported by the community: explicitly also set `ios.infoPlist.CFBundleURLTypes` in `app.json`, and always re-run a **clean** prebuild after any config change (stale native project state is a common self-inflicted cause). **Source: GitHub issue threads directly (WebSearch-surfaced titles/URLs). Confidence: Medium** — I read issue titles/summaries via search, not the full issue thread bodies, so I can't confirm current maintainer status (open/fixed) as of today.
2. **Android `DEVELOPER_ERROR` (status code 10).** Per the library's own troubleshooting doc, this is "a configuration mismatch between your app and the server-side setup" — almost always a SHA-1 fingerprint that wasn't registered for the exact signing config used to build the APK (debug vs release vs EAS Build credential vs Play App Signing cert all differ). The doc points to a "Configuration Doctor" tool to diagnose. **Source: official troubleshooting page, direct fetch. Confidence: High.**
3. **Package name / `applicationId` mismatch.** The Android `AndroidManifest.xml` package must exactly match what's registered in Google Cloud Console / Firebase. **Source: official docs, direct fetch. Confidence: High.**
4. **API-shape drift from tutorials.** Because of the `userInfo.*` → `userInfo.data.*` breaking change (Q3), a large fraction of blog posts/StackOverflow answers online reference the OLD flat shape. Following a stale tutorial silently produces `undefined` for `idToken`/`user` fields rather than an error. **Source: WebSearch synthesis of migration commentary. Confidence: Medium** (I could not pin the exact version number where this landed — see Unverified).
5. **CJS/ESM interop for the backend verification package** is a real, documented class of failure for OTHER stacks (WebSearch surfaced `better-auth`+`jose` and `langchainjs`+`google-webauth` ERR_REQUIRE_ESM issues) — but as established in Q9, this specific repo's Nest app is already pure ESM, so it is **not** expected to hit this class of failure. Flagging it here only so it's not silently missed if `apps/api`'s ESM config were ever reverted to CJS.
6. **Confusing `serverAuthCode` with `idToken`.** Because `serverAuthCode` requires the additional `offlineAccess: true` flag (Q7), a common mistake pattern (seen across generic OAuth tutorials, not specific to this library) is to configure `offlineAccess: true` "just in case," which triggers an extra consent screen for offline API access the app doesn't need — unnecessary UX friction for an auth-only integration. **Confidence: Medium** (general pattern reasoning, not from a specific cited incident for this exact library).
